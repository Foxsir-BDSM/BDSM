# 第一部分：为什么能合并（本质论证）

现在的两块，剥掉外壳后是**同一种东西**：

| 维度 | 任务区现状 | 知识区现状 |
|:---|:---|:---|
| 存储 | GitHub 分支 `tasks` | GitHub 分支 `knowledge` |
| 文件格式 | Markdown + frontmatter | Markdown + frontmatter |
| 编辑器 | EasyMDE（纯文本域） | EasyMDE（纯文本域） |
| 列表渲染 | `.task-card` | `.article-card` |
| 详情渲染 | `detail.html`（4 种语法的伪 Markdown） | `article.html`（4 种语法的伪 Markdown） |
| 权限 | `checkPermissions()` 分层 | `checkPermissions()` 分层（**逐行相同**） |
| 缓存 | `list_tasks_tasks` / `detail_tasks_*` | `list_knowledge_articles` / `detail_knowledge_*` |
| 差别 | **只有 `BRANCH` / `PATH` / 分类选项 / CSS 前缀** | 同左 |

代码重复度 **95%**。两者本质都是「一篇带元数据的富文本内容」——
差别只在**内容该用什么结构承载**，而不是该不该分成两个模块。

**结论**：合并为一个板块，用**发布类型（Post Type）**区分结构。

## 2.2 顶层功能划分（5 个域）

│  欲炼之途（统一内容板块）                                  │
├──────────────────────────────────────────────────────────┤
│  ① 内容发布域    4 种发布类型 + 结构化编辑器（核心）        │

## 2.3 ① 内容发布域 —— 4 种发布类型

这是整个设计的核心：**不同类型的发布，用不同的结构承载**。

| # | 类型 | 适用 | 结构复杂度 | 对应你给的参考 |
|:---:|:---|:---|:---:|:---|
| A | **玩法任务** | 有明确步骤的实践 | ★★★★ | `编号任务卡`（编号/等级/主题/道具/步骤/检查） |
| B | **主题合集** | 围绕一个主题的多条目 | ★★★ | `口罩.txt`（羞辱篇/残虐篇 → 分条） |
| C | **分级清单** | 打分、量表、对照表 | ★★★★ | `M自评报告`（SSS/SS/S 量表）、`m题.txt`（-1~10） |
| D | **见解随笔** | 自由表达、经验、科普 | ★ | 你要求的"用户发布自己的见解" |

> 原「知识区」的文章 = D 类；原「任务区」的内容 = A / B 类。
> 这样就自然完成了合并，且**不需要两种编辑器**——是一个编辑器带 4 套字段组。

# 第四部分：安全与治理（必须内建）

参考资料里有两份文档明确写了安全铁律与高风险红线，而**当前的任务卡完全没有这些**。
编辑器必须把这些变成**结构性约束**，而不是靠发布者自觉。

## 4.1 风险分级（发布时必选）

| 等级 | 判定 | 编辑器行为 | 详情页渲染 |
|:---:|:---|:---|:---|
| 🟢 低 | 无身体损伤风险 | 正常发布 | 无提示 |
| 🟡 中 | 有不适但可逆 | 提示补充中止条件 | 顶部黄条提示 |
| 🟠 高 | 可能造成可逆损伤 | **必填**「中止条件」与「后护理」才能发布 | 顶部橙条 + 默认展开但置顶警示 |
| 🔴 极高 | 有不可逆伤害风险 | **必填**全部安全字段 + **勾选知情确认**才能发布 | **默认折叠**，需点击「我已了解风险，展开查看」 |

> 决策 1 落地：不拦截。平台的定位是「标注与知情」，把判断权交给读者，
> 同时通过折叠 + 确认把「误触」的可能性降到最低。

## 4.2 高风险提示（替代原红线拦截）

不再做关键词自动拒绝，改为**辅助提示**：当正文命中以下类别时，
编辑器**弹出提醒**建议提高风险等级并补全安全字段（可忽略继续发布）：

不可逆伤害 / 呼吸循环阻断 / 涉未成年人 / 未同意的第三方 /
以医疗系统为道具 / 财务毁灭或社死自毁 / 真实身份信息胁迫

> 提示语示例：「检测到内容可能涉及不可逆伤害，建议把风险等级调为『极高』并补全中止条件与后护理。是否继续？」
> —— 三个按钮：调整等级 / 补全字段 / 仍要发布

## 4.3 安全字段（高/极高风险强制）

| 字段 | 说明 |
|:---|:---|
| 安全词 / 安全信号 | 默认预填 Red / Yellow / Green |
| 中止条件 | 出现什么必须立刻停止 |
| 独自执行限制 | 是否禁止独处执行 |
| 紧急预案 | 联系方式、就近就医提示 |
| 事后观察 | 观察时长与要点 |

## 4.4 决策记录：为什么不拦截

你选择了「仅标注不拦截」。我把当时的考量记录在此，供后续追溯：

**支持拦截的理由**（未被采纳）
1. 不可逆 = 无法事后补救，「同意」无法覆盖已发生的永久损伤
2. 平台责任：内容一旦发布即构成传播，风险不在发布者个人
3. 参考资料中大量条目描述永久伤害，入库后平台性质会变化

**你选择不拦截的取向**
- 保留表达自由，把判断权交给读者
- 平台定位为「同好交流与标注」，不做内容裁判

**因此采取的折中**：不拦截，但把「知情」做到位——
强制风险标注 + 高/极高风险默认折叠 + 发布前知情确认 + 详情页显著警示。
这样既保留表达，又把误触概率降到最低。

# 第六部分：数据与迁移

## 6.1 存储结构（GitHub 单分支 + 类型字段）

```
foxsir-content
└── branch: content          ← 新的统一分支
    └── posts/
        └── {slug}.md        ← frontmatter 承载结构化数据
```

**为什么仍是 Markdown**：结构化字段放 frontmatter（YAML/JSON），正文放步骤或随笔。
好处：可读、可 diff、GitHub 上能直接改、迁移成本低。

frontmatter 草案（A 类）：

```yaml
---
type: task
title: 标题
slug: slug
summary: 一句话摘要
risk: low | mid | high | extreme
visibility: public | member | private
tags: [束缚, 居家, 短时]
duration: { value: 30, unit: minute }
setup:
  scenes: [居家独处]
  times: [夜晚]
  env: 独立卫浴、可锁门
  pre: 需空腹
  mental: 预期紧张感
props:
  - name: 软绳
    required: true
    alt: 领带
    safety: 避开颈部
steps:
  - order: 1
    text: 步骤说明
    measure: 15 分钟
    caution: 出现麻木立即停止
    abort: 出现麻木
checkpoints:
  - text: 过程记录
    proof: [photo]
    count: 1
    required: true
aftercare:
  cleanup: ...
  body: ...
  emotion: ...
  observe: 24 小时
---
正文（可选补充说明）
```

## 9.3 架构要点

**schema 驱动**：`content-types.js` 一处定义，三处消费——
编辑器表单、详情页渲染、列表卡片。新增字段只改这一个文件，三处自动生效。

**为什么结构化数据放正文而非 frontmatter**：
`content-manager.js` 的 `parseFrontmatter` 只返回固定字段，未知 key 会被丢弃。
因此改用正文内嵌 JSON 区块（```` ```json foxsir-post ````），读回时不丢失，
frontmatter 仍保留可读的基础信息（标题/作者/风险/可见性等）。

**落盘格式**：
```
---
title / slug / content_type / risk / visibility / summary /
cover_url / is_public / tags / author_nickname / created_at
---

```json foxsir-post
{ "type": "...", "meta": {...}, "data": {...} }
```

（可选）Markdown 正文
```
