# 〇、先给结论

**绑定方案：以「邮箱」为钥匙，由站点在打开表单时通过 URL 参数隐式传入，表单侧设为隐藏字段。**

用户全程无感——他只是在已登录状态下点了一个按钮。

**为什么这把钥匙是对的**：

| 候选 | 唯一性 | 用户可控 | 能否隐式获取 | 结论 |
|:---|:---:|:---:|:---:|:---|
| `user.id`（UUID） | ✅ | ❌ | ✅ | 最准，但**用户看不到也记不住**，无法手动核对 |
| **`user.email`** | ✅ | ✅ | ✅ | ★ **选它** |
| `nickname` | ❌ 可重复 | ✅ | ✅ | 只能作为兜底 |
| `联系方式`（QQ/微信） | ❌ | ✅ | ❌ | 与账号体系无关，不能作主键 |

**邮箱同时满足「系统唯一」与「用户自己知道」**——这一点很重要：
万一自动绑定失败，用户自己就能说清"我用哪个邮箱填的"，而你也能在后台核对。

**而且你的系统里这把钥匙已经存在了**：内容 frontmatter 已经有 `author_email` 字段
（`src/modules/content/js/content-types.js:435`）。只是目前没人填。

# 一、现状：四块功能各自为政

| 功能 | 数据存在哪 | 账号关联 | 问题 |
|:---|:---|:---|:---|
| **档案馆** | Fillout Tables（`taRmZxGFzF5`） | ❌ **无任何账号字段** | 只能按昵称猜；`my.html` 里那段"按昵称匹配"就是这么来的 |
| **任务/内容** | GitHub `content` 分支 | ⚠️ 有 `author_email` 字段但常为空 | 发布者归属不可靠 |
| **情景问卷** | 尚无 | — | 待建 |
| **个人页面** | Supabase `auth.users` + `user_metadata` | ✅ 天然有 `id` / `email` | 是唯一知道自己是谁的地方 |

**核心矛盾**：唯一知道"你是谁"的是 Supabase；内容与档案都活在它外面，
两边靠一个可重复的昵称勉强相连。

```
Supabase (知道你是谁)          GitHub / Fillout (存内容)
   user.id                        author_email: ''      ← 空的
   user.email                     author_nickname: '某某'
        │                                │
        └──────  靠昵称猜  ──────────────┘
                    ↑ 不可靠
```

# 二、绑定方案（三层策略）

## 第 1 层 · 隐式传入（主路径，用户零操作）

站点在跳转到表单时拼接 URL 参数：

```
https://forms.fillout.com/t/xxx?user_email=<登录邮箱>&user_nickname=<昵称>&uid=<user.id 前 8 位>
```

表单里：

| 字段 | 类型 | 设置 |
|:---|:---|:---|
| `user_email` | 隐藏字段 | 从 URL 参数取值，**锁定不可编辑** |
| `user_nickname` | 隐藏字段 | 同上，仅作兜底 |
| `uid` | 隐藏字段 | 同上，便于人工核对 |

依据：[URL Parameters/Hidden fields](https://www.fillout.com/help/url-parameters)、
[Use URL parameters in form embeds](https://www.fillout.com/help/embedded-url-parameters)。

**用户看到的就是"点一下按钮，表单打开"，他不知道也不需要在字段里填邮箱。**

## 第 2 层 · 幂等更新（防重复档案）

**同一个人重填 = 更新，不是新建。**

实现：以 `user_email` 为唯一键做 upsert。
Fillout 侧可用 [Pre-fetch records](https://www.fillout.com/help/pre-fetch-records)
在打开表单时先查该邮箱是否已有档案，有则回填。

好处：
- 用户改主意、补信息，不会产生第二条档案
- 后台不需要人工去重

## 第 3 层 · 后台补录（兜底）

未登录就填、或从外部直接打开表单的情况，`user_email` 为空。

后台给管理员一个「待绑定」列表：

| 提交时间 | 昵称 | 联系方式 | 操作 |
|:---|:---|:---|:---|
| 10-03 14:22 | 某某 | tg@xxx | [绑定到账号 ▾] |

管理员选一个账号即可完成绑定。**这是人工兜底，不是主路径**——正常流程不会走到这里。

# 三、统一身份结构（让四块功能说同一种话）

现在四块各有各的字段名。统一成这样：

```js
// 任何内容、任何档案、任何提交，都带这四项
{
  author_uid:   'a1b2c3d4',        // Supabase user.id 前 8 位（便于核对）
  author_email: 'user@example.com', // ★ 绑定主键
  author_nickname: '某某',           // 展示用
  author_identity: 'female_M',      // 4 身份之一，决定可见性与筛选
}
```

**为什么加 `author_identity`**：你的档案馆已经要按身份筛选了
（男女馆合并后由表单的「身份」字段承担）。如果内容也带身份，
就能反过来做「这个任务适合哪种身份」的推荐。

# 四、四个功能的连通（这是你问的核心）

```
                    ┌─────────────────────────┐
                    │     个人页面（枢纽）      │
                    │  /my.html               │
                    └───────────┬─────────────┘
                                │
        ┌───────────────┬───────┴────────┬───────────────┐
        ▼               ▼                ▼               ▼
   ┌─────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
   │ 我的档案 │    │ 我的任务  │    │ 情景问卷  │    │ 我的发布  │
   │ 档案库   │    │ 任务接取  │    │ 问卷结果  │    │ 内容板块  │
   └────┬────┘    └────┬─────┘    └────┬─────┘    └────┬─────┘
        │              │               │               │
        └──────────────┴───────┬───────┴───────────────┘
                               ▼
                    全靠 author_email 串起来
```

## 4.1 档案 ↔ 情景问卷：**画像驱动档案**

这是最有价值的一条。

| 方向 | 机制 |
|:---|:---|
| 问卷 → 档案 | 填完问卷，**答案自动写入档案对应字段**（兴趣矩阵、边界、安全习惯） |
| 档案 → 问卷 | 档案里"兴趣程度 1–5 分"直接来自问卷的 28 个玩法条目问题 |
| 增量更新 | 用户重填问卷，档案只更新变化的部分，不清空其他字段 |

**设计要点**：问卷不是独立产物，它是**档案的一种填写方式**。
情景问卷 = 带情境包装的档案填写流程。

## 4.2 档案 ↔ 任务接取：**身份与偏好决定可接任务**

| 方向 | 机制 |
|:---|:---|
| 档案 → 任务 | 任务可标注「适合身份」（男S/女M…）与「需要道具」；档案里的偏好矩阵决定推荐排序 |
| 任务 → 档案 | 完成记录写回档案的「任务履历」区（次数、难度分布、完成率） |
| 安全联动 | 档案里的**红线**与任务里的**风险等级**交叉校验，冲突时提示 |

## 4.3 任务 ↔ 个人页面：**接取状态是留痕**

`my.html` 的「接取的任务」Tab（现在是空态）接上：

| 状态 | 含义 |
|:---|:---|
| 已接取 | 点了接取，未提交 |
| 进行中 | 已提交部分凭证 |
| 待确认 | 凭证齐了，等审核 |
| 已完成 | 审核通过，计入档案履历 |
| 已放弃 | 主动放弃或超时 |

每条记录：`user_email` + `task_slug` + 状态 + 时间戳 + 凭证链接。

## 4.4 情景问卷 ↔ 任务：**问卷可作为任务的前置**

有些任务有前置条件（比如"确认你了解安全词机制"）。
问卷的某个章节可以充当**前置资格**：答完才解锁接取按钮。

# 五、存储分工（我的建议）

你提到两个选项：Fillout 表单 vs. 自建编辑器 + GitHub。
**我的建议是分工，不是二选一。**

| 数据 | 存哪 | 理由 |
|:---|:---|:---|
| **静态内容**（任务正文、情景问卷题目、知识） | **GitHub** `content` 分支 | 版本可追、可 diff、后台可改、与现有 content 模块复用 |
| **用户提交**（档案、问卷答案、任务接取记录） | **Supabase 自建表** | 要按 `author_email` 索引与更新，GitHub 做不到 |
| **图片/影像** | Supabase Storage | 已有 `avatars` bucket 的模式可复用 |

## 5.1 需要新建的 Supabase 表

```sql
-- 档案（替代/镜像 Fillout Tables）
create table archive_profiles (
  user_email   text primary key,          -- ★ 绑定键
  user_uid     text,
  identity     text,                      -- male_S / female_S / male_M / female_M
  orientation  text,
  data         jsonb,                     -- 全部字段
  updated_at   timestamptz default now()
);

-- 问卷提交
create table questionnaire_submissions (
  id          uuid primary key default gen_random_uuid(),
  user_email  text references archive_profiles(user_email),
  form_slug   text,
  answers     jsonb,
  submitted_at timestamptz default now()
);

-- 任务接取
create table task_acceptances (
  id          uuid primary key default gen_random_uuid(),
  user_email  text references archive_profiles(user_email),
  task_slug   text,
  status      text default 'accepted',
  proof       jsonb,
  accepted_at timestamptz default now(),
  updated_at  timestamptz default now()
);

-- 待绑定队列（第 3 层兜底）
create table unbound_submissions (
  id          uuid primary key default gen_random_uuid(),
  source      text,        -- archive / questionnaire / task
  raw         jsonb,
  created_at  timestamptz default now()
);
```

**安全注意**：这些表的 RLS 策略要设成
「用户只能读写 `user_email = 自己邮箱` 的行」，管理员可读全部。
你现在只有 `avatars` 一个自建表，建表时要一并把 RLS 配好——否则默认开放。

# 六、与「档案馆合并」决策的一致性

你最近刚决定：

- ✅ 两个档案馆合并为一套字段
- ✅ 默认过滤**不再依赖馆别**，改由表单的「身份」字段承担

这个决定和本方案**天然契合**：

| 已有决策 | 在本方案里的角色 |
|:---|:---|
| 档案的「身份」字段 | = 统一身份结构里的 `author_identity` |
| 档案的「取向」字段 | 决定默认筛选 |
| `FILTER_FIELDS` 占位 | 一旦你补上两个字段 ID，筛选与绑定**同时生效** |

也就是说：**你补那两个字段的时候，顺手把 `user_email` 隐藏字段一起加上**，
绑定就一次做完了，不需要二期改造。

# 七、一个必须提醒的安全边界

第 1 层的 URL 参数方案，**在"用户从本站登录后进入"这个前提下是安全的**。

但如果有人手工构造 URL：

```
...?user_email=别人的邮箱
```

就能把内容写到别人名下。

**风险有多大？** 说清楚：

| 场景 | 影响 |
|:---|:---|
| 恶意用户冒充他人提交档案 | 会污染他人档案 ← **这是真实风险** |
| 误填自己的其他邮箱 | 只影响自己 |

**三种应对，按成本排序**：

| 方案 | 成本 | 效果 |
|:---|:---|:---|
| ① 表单页要求登录 + 服务端校验 | 低 | 挡住了"未登录直接构造 URL"，但挡不住已登录用户冒充别人 |
| ② **签名令牌**（HMAC） | 中 | ★ 真正解决。站点生成 `email+签名`，Worker 验签后才写入 |
| ③ 只允许本站嵌入 iframe | 低 | 挡住外部直接访问，但可被绕过 |

**我的建议**：先上 ①，如果将来档案涉及真实身份与影像（现在已经涉及了），
就补 ②。签名令牌需要一个小后端——**那个 Workers 地址正好可以承担这个角色**，
前提是它是你的。

# 十、一句话总结

**个人页面是枢纽，`author_email` 是血管，GitHub 存内容，Supabase 存关系。**

绑定不需要用户做任何事——他只要在登录状态下点一下入口，
